# 세션 회고

목적은 두 가지다.

1. **사용자가 같은 지적을 두 번 하지 않게 만든다.**
2. **같은 실수를 반복하지 않게 해서 토큰과 시간을 아낀다.** 잘못된 방향으로 간 작업, 되돌린 변경, 다시 설명하게 만든 왕복은 전부 낭비다. 실수 한 번은 그 자리에서 끝나지 않고 재작업 전체를 태운다.

그래서 한 번이라도 드러난 결함은 그 자리에서 고친다. 두 번째 사례를 기다리지 않는다.

세션 기록에서 실제 근거를 찾아 하네스를 고친다. 기억이나 추측으로 쓰지 않는다.

## 인자와 실행 모드

```
[세션수] [--apply]
```

| 인자 | 기본값 | 뜻 |
|---|---|---|
| 세션수 | `1` | `1`이면 지금 이 대화 세션. 2 이상이면 현재 저장소의 최근 N개 세션 |
| `--apply` | 없음 | 이 플래그가 있을 때만 파일을 쓴다 |

**기본은 지금 이 대화 세션이다.** 사용자가 기간이나 범위를 말하지 않았다면 방금까지 함께 한 작업을 회고하라는 뜻이다. 임의로 며칠 치를 끌어오지 않는다. 세션 여러 개를 보면 지금 대화와 무관한 개선점이 섞여 나온다.

**기본은 미리보기다.** `--apply` 없이 실행하면 무엇을 어디에 어떻게 고칠지 보여주기만 하고 **어떤 파일도 쓰지 않는다.** 지침 문서는 이후 모든 세션에 영향을 주므로, 사용자가 내용을 보고 결정하게 한다. **승인과 실행을 한 손에 쥐지 않는다.**

`--apply`가 있어도 **이번 실행에서 방금 제시한 개선안만** 적용한다. 이전 실행의 제안이나 대화 중에 나온 다른 아이디어를 끼워 넣지 않는다.

### 수정 범위는 현재 저장소뿐이다

**고치는 파일은 언제나 현재 저장소 안에 있다.** 다음은 수정 대상이 아니다.

- `~/.claude/` 아래 개인 설정 — 저장소에 커밋되는 스킬이 사용자 홈의 개인 영역을 건드려서는 안 된다
- 다른 저장소의 문서

이 영역에 해당하는 개선점은 **찾아서 알리되 고치지 않는다.** 붙여넣을 수 있는 문구까지만 내고, 넣을지는 사용자가 정한다.

## 1. 세션 수집

회고의 단위는 **대화 세션 하나**다. 프로젝트가 아니다. 한 세션이 한 덩어리의 작업이고, 같은 문제가 세션을 넘어 다시 나타날 때 그것을 반복이라 부른다.

### 대상 기록 찾기

**현재 세션의 ID는 스크래치패드 디렉토리 경로에 들어 있다.** 그 ID로 기록 파일을 특정한다. 가장 최근에 수정된 파일을 고르면 안 된다 — 다른 세션이 나중에 쓰이면 그쪽이 잡힌다.

```bash
SID=<현재 세션 ID>
F=$(find "$HOME/.claude/projects" -name "$SID.jsonl" | head -1)
```

세션 여러 개를 요청받았다면 현재 저장소의 기록을 오래된 순으로 N개 잡는다.

```bash
P=$(git rev-parse --show-toplevel 2>/dev/null || pwd)
D="$HOME/.claude/projects/$(printf '%s' "$P" | sed 's/[/.]/-/g')"
ls -tr "$D"*/*.jsonl | tail -N
```

### 발화 추출

각 기록 파일에 대해 실행한다. 사용자 발화만 뽑고, **직전 Claude 턴 요약과 발화 uuid를 함께** 낸다.

```bash
jq -s -r '
  def utext: (.message.content | if type=="string" then .
              else (map(select(.type=="text").text) | join(" ")) end);
  def asum: if . == null then "-"
            else ((.message.content // [])
                  | map(if .type=="tool_use" then .name
                        elif .type=="text" then (.text | gsub("\\s+";" ") | .[0:80])
                        else empty end)
                  | join(", ") | .[0:120]) end;
  reduce .[] as $r ({prev: null, out: []};
    if $r.type=="assistant" and $r.isSidechain!=true then .prev = $r
    elif ($r.type=="user" and $r.isSidechain!=true and $r.isMeta!=true
          and ($r.toolUseResult | not))
      then .out += [{u: $r, a: .prev}]
    else . end)
  | .out[]
  | (.u | utext) as $raw | select($raw | type=="string")
  | ($raw | gsub("\\s+";" ")) as $t
  | select($t | test("^<(command-name|command-message|local-command|bash-input|task-notification|system-reminder|hook|ide)") | not)
  | select($t | length > 4)
  | "    ↳ 직전: " + (.a | asum) + "\n> [" + (.u.uuid[0:8]) + "] " + ($t[0:400])
' "$F"
```

이 명령을 줄이거나 바꾸지 않는다. 각 조각에는 이유가 있다.

- `reduce`로 직전 assistant를 추적한다 — **원인을 판정하는 유일한 근거다.** 이것 없이는 "왜 그 말이 나왔는지" 알 수 없다
- `isSidechain` 제외 — 서브에이전트 대화는 사용자 발화가 아니다
- `toolUseResult` 제외 — 도구 결과도 `type: user`로 기록된다
- `test("^<(...)")` 제외 — 시스템 메시지가 발화로 집계되면 신호가 오염된다
- `-s`(slurp) 필수 — 레코드 간 순서를 봐야 직전 턴을 찾을 수 있다

**결과가 0건이면 회고를 진행하지 않는다.** 세션 ID나 경로가 틀린 것은 아닌지 확인하고, 정말 발화가 없으면 그 사실을 그대로 보고한다. 수집 실패를 "개선점 없음"으로 보고해서는 안 된다.

`.jsonl`은 레코드 하나가 한 줄이고 길이가 2만 자에 이르므로 **grep으로 앞뒤 맥락을 볼 수 없다.** 위 출력으로 부족할 때만 uuid로 정확히 집어 조회한다.

```bash
jq -r 'select(.uuid | startswith("<uuid8>"))' "$F"
```

## 2. 개선 신호 찾기

사용자 발화 중 다음을 찾는다.

- **되돌림** — 진행한 작업을 폐기시키거나 원복시킨다 (낭비가 가장 큰 신호)
- **교정** — 방금 한 작업을 다시 시킨다
- **반려** — 제안한 접근을 거부한다
- **재질문** — 같은 것을 다시 묻는다 (첫 설명이 불충분했다는 뜻)
- **재확인 요구** — 이미 알려준 정보나 이미 확인한 사실을 또 다루게 한다
- **범위 이탈 지적** — 시키지 않은 것을 했다고 지적한다
- **근거 부족 지적** — 확인 없이 단정했다고 지적한다
- **형식 요구** — 출력 방식이나 톤을 반복해서 요구한다

### 개선점이 아닌 것

이걸 실수로 집계하면 지침이 오염된다.

- 사용자가 요구사항을 바꾼 것
- 정보를 추가로 제공한 것
- 자연스러운 후속 질문
- 외부 요인으로 인한 실패(네트워크, 서드파티 장애, 권한)

애매하면 기록 파일에서 앞뒤를 확인한다. 확인해도 애매하면 **제외한다.** 놓치는 것보다 잘못 넣는 게 나쁘다.

## 3. 고칠 것인지 판단

**빈도는 기준이 아니다.** 한 번만 나온 지적도 즉시 반영한다. 두 번째를 기다리는 것은 같은 실수를 한 번 더 당하겠다는 뜻이다.

기준은 "몇 번 나왔나"가 아니라 **"하네스를 고치면 막을 수 있나"**다.

**반영한다:**
- 지침·문서·도구 설정으로 예방할 수 있는 것
- 같은 상황이 오면 또 발생할 것
- 지금 바로 적용 가능한 행동 규칙으로 쓸 수 있는 것

**반영하지 않는다:**
- 그 순간에만 유효한 맥락 (특정 PR 번호, 특정 장애 대응)
- 규칙으로 옮기면 일반론밖에 안 되는 것
- 이미 구조가 바뀌어 재발할 수 없는 것

반복 횟수는 **우선순위**를 정할 때만 쓴다. 여러 세션에 걸친 것을 먼저 다룬다. 한 번 나왔다고 버리지 않는다.

묶는 기준은 표현이 아니라 **원인**이다. "비유 쓰지 마"와 "일반론 말고 코드 근거로 말해"는 문장은 다르지만 원인은 같을 수 있다. 원인이 같으면 하나로 묶어 한 곳만 고친다.

### 지난 회고가 먹혔는지 먼저 본다

지침 문서가 최근 언제 어떻게 바뀌었는지 확인한다.

```bash
git log --oneline -5 -- CLAUDE.md AGENTS.md .claude/ docs/
```

거기서 이미 다룬 문제가 **그 변경 이후 세션에서 또 나왔다면 그 지침은 실패한 것이다.** 문구를 강화하지 말고 한 단계 아래(커맨드·훅)로 내린다. 세션이 오래된 것부터 정렬돼 나오므로 시점 비교가 된다.

이 확인을 건너뛰면 "이미 문서에 있는데 또 어겼다"는 판정 자체가 불가능해지고, 매번 같은 문구만 다시 쌓게 된다.

## 4. 어디에 쓸지 판단

미리 정해진 파일은 없다. **범위**와 **부품**을 순서대로 정한다.

먼저 저장소의 문서 구조를 확인한다: `./CLAUDE.md`, `./.claude/`(docs·커맨드·스킬), `./docs/`, `./AGENTS.md`. 배치 관습은 프로젝트마다 다르므로 **기존 구조를 먼저 보고 그 관습을 따른다.**

### (1) 범위 — 어디까지 적용되는 개선점인가

개선점의 성격을 보고 정한다. 이 저장소가 아니어도 똑같이 발생할 일인지 자문한다.

| 개선점의 성격 | 위치 |
|---|---|
| 이 저장소의 도메인·스택·팀 규약에 묶인 것 | 그 저장소 안. **여기만 고친다** |
| 저장소와 무관한 작업 방식·소통 방식 | 개인 영역(`~/.claude/`). **고치지 않고 알리기만 한다** |

근거가 이 저장소 세션뿐이라는 점을 개인 영역 후보에는 함께 밝힌다.

### (2) 부품 — 하네스의 어디를 고칠 것인가

고칠 수 있는 것은 문서만이 아니다. 아래로 갈수록 강제력이 세다. **문서로 부탁해서 될 일과 도구로 막아야 할 일을 구분한다.**

| 개선점의 성격 | 고칠 곳 | 로드 비용 |
|---|---|---|
| 항상 지켜야 하는 짧은 규칙 | `CLAUDE.md` 본문 | 매 세션 전체 |
| 길고 특정 작업에서만 필요한 절차·체크리스트 | `docs/<주제>.md` + 본문에 포인터 한 줄 | 읽을 때만 |
| 왜 그렇게 정했는지의 기록 | 결정 기록 문서 | 읽을 때만 |
| 사용자가 명시적으로 부르는 절차 | 커맨드 정의 | 호출 시 |
| 모델이 상황을 보고 스스로 불러야 하는 절차 | 스킬 정의 | description만 상주 |
| 별도 컨텍스트에서 독립적으로 조사·검토 | 에이전트 정의 | description만 상주 |
| 의지와 무관하게 **반드시** 실행돼야 하는 것 | 훅 (`settings.json`) — 항상 제안만 | 매번 결정적 실행 |
| 반복되는 권한 프롬프트 제거 | 권한 설정 (`settings.json`) — 항상 제안만 | — |

판단 기준은 하나다. **"지키길 바라는 것"은 지침이고, "반드시 실행돼야 하는 것"은 훅이다.** 지침은 확률적이라 어겨질 수 있고, 훅은 결정적이지만 잘못 걸면 작업을 막는다.

저장소에 자체 배치 규칙 문서나 하네스 담당 에이전트 정의가 있으면 **그쪽을 우선한다.** 이 표는 그것이 없을 때의 기준이다.

`CLAUDE.md`는 매 세션 전문이 컨텍스트에 올라간다. 여기 넣은 문장은 **모든 세션에 상시 비용**을 만든다. 짧고 항상 적용되는 것만 남긴다.

포인터는 그 저장소가 이미 쓰는 방식을 그대로 흉내 낸다. 없으면 `세부 가이드: <경로>` 한 줄이면 된다.

**같은 지적이 이미 문서에 있는데도 또 나왔다면, 문구를 키우는 대신 한 단계 아래(커맨드·훅·설정)로 내리는 것을 검토한다.** 지켜지지 않는 지침은 더 크고 굵게 써도 지켜지지 않는다.

**기존 문서 우선.** 같은 주제를 다루는 문서가 이미 있으면 새 파일을 만들지 않는다. 후보가 여럿이면 가장 좁은 범위의 문서를 고른다. 새 파일 생성은 마지막 수단이다.

## 5. 반영

**이미 문서에 있는데도 어겼다면, 항목을 추가하지 말고 기존 항목을 고친다.** 안 지켜졌다는 건 그 지침이 추상적이거나 눈에 띄지 않았다는 뜻이다. 같은 말을 한 번 더 쓰는 건 해결이 아니다.

결과물은 **지금 바로 적용 가능한 형태**여야 한다. "이런 점을 유의하자" 같은 감상은 하네스를 바꾸지 못한다. 그대로 붙여넣으면 동작하는 문장·설정을 쓴다.

문구 작성 규칙:

- 행동 가능하게 쓴다. `X 하지 마라` 보다 `X 상황에서는 Y 한다`
- 언제 적용되는지 판단 기준을 포함한다
- 근거는 세션에서 나온 실제 사례를 쓴다. 지어내지 않는다
- 기존 문서의 형식·톤·언어를 따른다
- 쓰다 보니 절차나 예시가 붙어 길어지면, 그때 별도 문서로 빼고 본문엔 포인터만 남긴다
- 같은 주제의 낡은 항목이나 중복이 보이면 추가하지 말고 합친다

`--apply` 없이 실행했다면 **여기서 멈춘다.** 개선안만 출력하고 파일은 건드리지 않는다.

`--apply`라면 쓰기 전에 `git status`로 **작업트리가 깨끗한지 확인한다.** 진행 중인 변경이 있으면 멈추고 알린다. 하네스 수정이 기능 변경과 한 diff에 섞이면 되돌릴 때 손으로 골라내야 한다.

`--apply`로 실행했다면 고친 뒤 무엇을 어디에 썼는지 경로와 함께 보고한다. 기존 내용은 보존하고 **필요한 부분만 덧붙이거나 고친다.** 문서를 통째로 다시 쓰거나 관련 없는 부분을 정리하지 않는다.

## 출력 형식

한눈에 보이는 표를 먼저 내고, 그다음 상세를 쓴다.

```
## 회고 결과 — 최근 N일 / 범위: <경로 또는 all> / 모드: 미리보기 | 적용

| # | 개선점 | 고칠 곳 | 동작 |
|---|---|---|---|
| 1 | <한 줄 요약> | <파일 경로> | 수정 |

## 상세

### 1. <원인 한 줄>
- 근거: <세션 제목> (<기록 파일 경로>)
- 반영 내용: <그대로 붙여넣을 수 있는 문장 또는 설정>

## 버린 것
- <검토했지만 제외한 것> — <이유>
```

`동작` 값은 넷뿐이다.

| 값 | 뜻 |
|---|---|
| 수정 | 기존 항목을 고친다 |
| 추가 | 새 항목을 넣는다 |
| 제안만 | 자동으로 쓰지 않는다. 사람이 판단해야 하거나 새 파일 생성이 필요한 경우 |
| 버림 | 반영하지 않는다. 이유를 남긴다 |

`--apply`가 있어도 항상 `제안만`으로 남기는 것이 있다.

- 훅·권한 설정(`settings.json`) — 동작을 기계적으로 바꾸는 변경이라 사용자가 직접 보고 넣어야 한다
- 새 파일 생성
- 개인 영역(`~/.claude/`)과 다른 저장소 — 수정 범위 밖이다

이때는 그대로 붙여넣을 수 있는 문장이나 설정 조각을 함께 낸다.

**재발 위험과 낭비 규모가 큰 순서로 정렬한다.** 되돌린 작업처럼 재작업을 통째로 태운 것이 맨 위에 온다. 빈도순이 아니다. 한 번만 나왔다는 이유로 뒤로 밀거나 빼지 않는다.

**버린 것도 남긴다.** 무엇을 검토하고 왜 제외했는지 보여야 판단을 신뢰할 수 있다. 한 줄씩만 쓴다.

고칠 게 없으면 `회고 결과: 반영할 개선점 없음.` 한 줄로 끝낸다. 회고랍시고 일반론을 지어내지 않는다.

## 다른 저장소에서 쓰기

이 스킬은 공유를 위해 저장소에 담겨 있지만 **어느 저장소에도 종속되지 않는다.** 개인 스킬로 연결해두면 모든 프로젝트에서 뜬다.

```bash
ln -sfn "$(pwd)/.claude/skills/retrospective" ~/.claude/skills/retrospective
```

저장소에서 스킬을 고치면 연결된 쪽에도 그대로 반영된다.

전제는 두 가지뿐이다. **Claude Code의 세션 기록**(`~/.claude/projects/`)과 **`jq`**. 실행 파일을 따로 두지 않으므로 이 문서 하나가 스킬 전부다.
