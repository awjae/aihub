**Chrome DevTools MCP로 로컬에 띄운 앱을 실제로 조작하며 E2E 검증합니다** — 로컬 스택 기동 → 실화면 조작 → 기준(TC·기획·디자인)과 대조 → 명백한 버그는 즉시 수정·재검증 → 결과 기록·집계 보고까지.

인자: `$ARGUMENTS` — **검증 대상 범위**. 기능·화면 이름(`로그인 폼 검증`), 이슈 식별자(형식 불문), TC 파일 경로/URL 중 무엇이든 받는다. 여러 개를 섞어 줘도 된다.

> lint·build·타입체크만 필요하면 이 커맨드가 아니다. `/verify-e2e`는 **실제 브라우저에서 사람이 하듯 써보는** 사후 검증 전용이다.

## 전제 — 없으면 하드 스톱

1. **Chrome DevTools MCP 연결.** 미연결이면 **여기서 멈춘다.** 스크린샷 없이 코드만 읽고 "검증했다"고 보고하지 않는다. MCP 설정(`.mcp.json` 또는 사용자 설정) 확인·재시작을 요청한다.
2. 검증 대상 구현이 **현재 브랜치에 체크아웃**되어 있을 것.

## Step 0: 대상 판별

- `$ARGUMENTS`에서 **검증 범위**와 **TC 경로/URL**을 분리한다.
- 범위가 비어 있으면 추론한다: `git branch --show-current`, `git log --oneline -10`, `git diff <기본브랜치>...HEAD --stat`. 바뀐 파일이 닿는 화면·기능이 곧 검증 범위다.
- **추론 결과가 불분명하거나 범위가 너무 넓으면 진행하지 말고 되묻는다.** 무엇을 검증하는지 모른 채 시작하면 판정 기준도 없다.
- TC가 지정되지 않았으면 저장소에서 후보를 찾는다(`test-case`, `tc`, `qa`, `.plan/` 등 경로에 범위 키워드가 든 CSV/MD/시트 링크). 없으면 Step 2에서 직접 만든다.

## Step 1: 기준(SoT) 수집

무엇과 대조할지 없으면 검증이 아니라 구경이다. 아래 중 **구할 수 있는 것을** 확보한다.

- **이슈/티켓** — 트래커 연동(`gh`, 전용 MCP·스킬)이 있으면 본문뿐 아니라 **코멘트와 첨부까지** 본다. 요구사항 변경은 본문이 아니라 코멘트에 있는 경우가 흔하다.
- **기획·정책 문서** — 저장소 `docs/`, README, 또는 사용자가 준 링크.
- **디자인** — Figma 등. 이미지는 `Read`로 실제로 연다. 텍스트 설명만 읽고 대조하지 않는다.
- 접근 수단(스킬·MCP)이 **있으면 쓰고 없으면 사용자에게 링크·파일을 요청**한다. 없는 도구를 가정하지 않는다. 기준이 하나도 없으면 그 사실을 밝히고 진행한다.

## Step 2: 검증 시나리오 확정

- **TC가 있으면**: 파싱해 대상을 확정한다. 이미 pass인 항목은 이번 변경이 건드린 영역만 회귀 검증하고, **미검증·fail 항목을 우선**한다.
- **TC가 스프레드시트면**: 시트 조회 수단이 있으면 그것으로 읽는다. **셀 배경색에 범례가 있는 시트가 흔하므로**(노랑=검증 필요, 회색=skip 등) 텍스트만 읽고 단정하지 않는다. 읽은 내용은 **로컬 스냅샷 파일로 떠서 이후 기록은 스냅샷에만** 한다(공유 문서 즉시 쓰기 금지 — Step 5 참조).
- **TC가 없으면**: 기준 문서·디자인에서 체크리스트를 도출해 로컬 파일로 저장한다 (컬럼: 분류, 시나리오, 기대 결과, 검증자, 결과). 목록을 사용자에게 한 번 보여주고 진행한다 (승인 대기 없이 이견만 받는 가벼운 확인).
- **"검증 불가"로 단정하기 전에 우회 수단을 먼저 검토한다**: 오프라인 에뮬레이션(실패 경로 유도), viewport 에뮬레이션(반응형), 테스트 데이터 임시 변경 후 원복(조건 재현), 시스템 시각·로케일 조작 등. 그래도 불가하면 사유를 남기고 넘어간다.

## Step 3: 로컬 스택 기동

1. **기동 방법을 저장소에서 찾는다.** `CLAUDE.md` → `package.json`(scripts) → `Makefile` → `docker-compose.yml` 순으로 확인하고, 진입 URL·포트·테스트 계정도 같은 곳에서 찾는다. **어디에도 없으면 지어내지 말고 사용자에게 묻는다.** 명령·포트·계정을 하드코딩하지 않는다.
2. **이미 떠 있는 스택의 재사용 판별은 포트가 아니라 프로세스로 한다.** 포트가 열려 있다는 사실은 *내가 검증하려는 그 서비스*가 떠 있다는 뜻이 아니다 — 다른 프로젝트나 이전 세션의 엉뚱한 서비스에 붙어 한참 뒤에야 알게 된다.
   ```bash
   pgrep -f "<서비스 프로세스 식별 문자열>" >/dev/null   # 기대 서비스가 맞는지 확인
   ```
   **기대 서비스의 프로세스가 확인될 때만** 재사용한다. 다른 것이 그 포트를 잡고 있으면 사용자에게 종료·교체 여부를 확인한 뒤 기동한다.
3. 기동은 백그라운드로 돌리고, **포트 준비 대기는 필요 포트 전부를 until-loop로 확인한다. foreground `sleep`으로 뭉개지 않는다.**
   ```bash
   for port in <PORT_A> <PORT_B>; do
     ok=0
     for i in $(seq 1 60); do
       lsof -iTCP:$port -sTCP:LISTEN -nP >/dev/null && { ok=1; break; }; sleep 2
     done
     [ "$ok" = 1 ] || { echo "PORT $port not ready"; exit 1; }
   done
   ```
   **타임아웃이면 진행하지 않는다.** 브라우저를 열어 빈 화면을 보는 대신 기동 로그에서 원인을 확인한다.
4. Chrome DevTools MCP `navigate_page`로 진입 URL을 연다. 로그인이 필요하면 1에서 확인한 계정을 쓴다.
5. 로그인·세션 이상(권한 오류, 무한 리다이렉트)은 **이전 세션이 남긴 stale 토큰이 원인인 경우가 많다** — `evaluate_script`로 `localStorage.clear()`·쿠키 정리 후 리로드해 한 번 확인한 뒤, 그래도 재현되면 버그로 다룬다.

## Step 4: 검증 루프 (핵심)

시나리오 단위로 **조작 → 판정 → 기록**을 반복한다.

### 조작 — Chrome DevTools MCP

- `take_snapshot`으로 uid를 확보 → `click`/`fill`/`press_key`로 상태를 재현 → `evaluate_script`로 정밀 값을 추출한다(텍스트·computedStyle·좌표). 눈으로 스크린샷만 보고 색·간격을 판정하지 않는다.
- **커스텀 컴포넌트는 JS `click()`으로 열리지 않는 것이 있다** (셀렉트·드롭다운·오버레이류. 합성 이벤트만 듣거나 pointer 이벤트를 요구한다). **MCP의 실클릭 도구를 기본으로 쓰고**, JS click은 단순 버튼에만 보조로 쓴다.
- **비동기 UI 감시는 타임아웃을 넉넉히.** 토스트·스낵바·에러 배너는 클라이언트 재시도가 모두 끝난 뒤에야 뜰 수 있다. 실패 UX 검증은 짧은 폴링 한 번으로 "안 뜬다"고 결론내지 말고 15초 이상 interval로 감시한다.
- **환경 조작은 `emulate`가 `resize_page`보다 신뢰할 만하다** — 실패 경로는 `emulate`(networkConditions: Offline), 레이아웃은 `emulate`(viewport). `resize_page`는 OS·창 상태에 따라 무시될 수 있다.

### 판정 — 눈에 보이는 diff ≠ 버그

차이를 발견하면 **반드시 해당 소스를 열어 원인을 확인한 뒤** 아래로 분류한다. 소스를 안 보고 분류하지 않는다.

| 분류 | 처리 |
|---|---|
| **코드 버그** | 즉시 수정 → 재검증 |
| **의도된 것** | 근거(코드·기준 문서)와 함께 pass |
| **상태·데이터 의존** | 데이터 조건을 맞춰 재시도. 못 맞추면 사유 기록 |
| **워딩·기준 애매** | 추측 수정 금지. 멈추고 사용자 판단 |
| **구조 차이** | 디자인/기준과 마크업 구조가 다르나 결과가 같은 경우. 근거를 남기고 pass |

- **명백한 버그**(누락 요소, 오탈자, 색·간격 불일치, 동작 안 함)는 즉시 수정 → 리로드로 **재검증**한 뒤 다음 항목으로. 수정 커밋은 저장소 컨벤션에 맞춘다.
- **TC 기대와 구현이 다른데 구현이 맞아 보이면** fail로 두지 말고 "기준 확인 필요"로 표기해 보고에 포함한다.

### 기록

- 검증자·결과(`pass` / `fail` / `N/A`) + ` — 특이사항`을 항목마다 남긴다.
- **fail → fix → 재검증 pass 이력을 남긴다**: `pass — 최초 구현 누락(fail) → 수정(<커밋>): <내용>`. 최종 pass만 적으면 무엇을 고쳤는지 사라진다.
- TC 문구 자체가 구버전이면 pass 처리하되 특이사항에 "TC 문구 갱신 필요"를 남긴다.
- **기록 대상은 항상 로컬 파일**이다. 공유 문서 반영은 Step 5.

### 테스트 데이터 원복 (규율)

검증을 위해 만든 데이터·설정 변경은 **검증 직후 원복**한다. 되돌릴 수 없는 조작(발송, 결제, 확정 전환, 삭제)은 **실행 전에** 사용자에게 확인받는다.

## Step 5: 마무리

1. 수정이 있었으면 저장소가 제공하는 검증 스크립트(lint·typecheck·build·test 중 **실재하는 것만**)를 돌린다. 없으면 없다고 보고한다.
2. 수정 커밋·push는 저장소 컨벤션을 따른다.
3. **집계 보고**: pass/fail/N/A/미검증 수, 발견한 불일치와 수정 내역(커밋), 기준 확인이 필요한 항목, 검증 불가 항목과 사유.
4. **공유 문서(스프레드시트 등) 반영은 여기서, 사용자 확인 후 일괄.** 쓸 대상과 범위를 먼저 보여주고 승인을 받는다 — 남에게 즉시 보이고 되돌리기 어렵기 때문에 검증 중 실시간 반영은 하지 않는다.
5. 로컬 스택·브라우저 **종료 여부를 사용자에게 묻고** 정리한다.

## 알려진 함정

- **검증용으로 생성된 산출물·캐시·암호화 파일을 커밋하지 않는다.** 빌드가 소스 트리를 더럽히는 저장소가 있으므로 커밋 전에 `git status`를 확인한다.
- **실시간 반영(소켓·구독)이 안 될 때**는 대개 UI가 아니라 데이터 레이어다 — 쿼리 응답의 식별자 누락, 구독 미설정, 뮤테이션 selection 누락, 클라이언트 캐시 리스트 병합 부재를 먼저 본다.
- **DB·외부 상태 확인이 필요하면 읽기 전용 수단만 쓴다.** 검증 중 쓰기는 Step 4의 원복 규율을 따른다.
